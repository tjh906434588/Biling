## 三、AI 拟人优化（针对朱雀 AI 检测：第1章 33% 人工，第2章全疑 AI）
- 判断：**需要处理**。第2章比第1章更"AI"的典型原因是跨章节奏趋同——
  续写时模型会沿用上一章的句子节奏，导致句长变异系数下降、连接词密度上升。
- 改动：
  1. `backend/app/agents/l1.py`：新增【L1·反「AI 味」量化自检】7 条硬指标
     （极短句 ≥15%、连接词密度 ≤3.5/千字、禁止排比与总分总、允许口语瑕疵、
      禁止每段感悟升华、对话像真人说话、结尾落在具象画面而非总结）。
     novelist 与 reviser 共用。
  2. `backend/app/agents/novelist.py`：`temperature` 0.75 → **0.82**，削弱分布过度规整。
  3. 同上：在 `build_context` 里调用本地 `services.detector.detect()`，把**上一章实测指标**
     （句长变异系数 / 极短句占比 / 连接词密度）作为 L3 提示喂给模型，明确要求本章不要延续上一章节奏。
  4. `backend/app/agents/reviser.py`：修订提示改为引用 L1 量化自检 + 以本章实测值为修订目标，删掉重复规则。
- 用户表示"可能不用管"，所以以上改动**随时可回退**（temperature 与 L1 段落都在文件里独立成块）。

## 四、环境 / 工具备忘
- Git Bash 的 PATH 有时缺 coreutils（`ls`/`find`/`dirname` 报 command not found），
  命令前加 `export PATH="$PATH:/d/TaskUtils/Git/usr/bin"` 修复。
- 本模型 Read 读 png 会返回 image filtered，**看不了截图**。
  视觉回归改用 `scripts/shot.mjs` 的 `PROBE` 环境变量走 CDP `Runtime.evaluate` 取 innerText 做 DOM 断言。
- 面板切换在 PROBE 里点按钮不可靠，直接访问 `?tab=write|settings|outline|detect`，
  等待条件用 `header h1 textContent !== '未命名作品'` 保证数据已加载。
- Next dev 源站保护：测试必须走 `http://localhost:3000`，不能用 127.0.0.1。
- **环境里有 http_proxy（127.0.0.1:51813）**，curl 本地服务会先走代理 → 后端没起来时返回 **502 而不是 000**，
  容易误判成"服务还活着"。探测本地端口一律加 `curl --noproxy '*'`；shot.mjs 用 `NOPROXY=1`。
- Bash 工具里用 `cmd &` 起的后台进程会随命令返回被杀；要常驻服务必须用 Bash 工具的 `run_in_background=true`。
- `taskkill /PID x /F` 在 Git Bash 下会被路径转换搞坏，加 `MSYS_NO_PATHCONV=1`；`wmic` 在安全黑名单里，别用。

## 五、评价与正文版本对齐（用户提问引出，已实现）
- 用户疑问：写作页「评价与优化」看不出对应哪一版正文（初稿 / 按评价优化）。
- 查证：`quality_reviews.chapter_version_id` 一直有值（`_persist_critic` 取该章 active 版本），
  但 `ReviewRead` schema **没把版本字段吐给前端**；更严重的是 `handleRevise` 用的是
  `activeChapter.active_content`（当前激活版）而非"这条评价当初评的那个版本" → 会拿旧评价改新正文。
- 真实数据坐实：第 1 章 88 分评 v1、84 分评 v2，而当前激活的是 v1 → 84 分那条本该不可操作。
- 改动：
  1. `schemas/chapter.py` 的 `ReviewRead` 增加 `chapter_version_id / version_no / version_source / is_current`。
  2. `api/chapters.py` 的 `list_reviews` 改为 select 三元组 `(QualityReview, Chapter, ChapterVersion)`，
     `is_current = bool(ChapterVersion.is_active)`。保持 join（非告警类评价才入列）。
  3. 前端 `lib/api.ts` 的 `QualityReview` 同步加字段；`ReviewCard` 标题后加版本徽标
     （`v2 按评价优化 · 旧版本` / `v1 初稿 · 当前正文`）。
  4. **只有 `is_current` 的评价才渲染「按评价优化本章」按钮**；旧版本卡片只展示并提示
     "评价不再对得上…点版本列表的 vN 还原后再优化"。`handleRevise` 里再加一道 `is_current` 兜底。
  5. `handleSelectVersion` 末尾补拉 reviews（切版本 → 评价归属会变，必须重刷）。
- 用户选的行为：**不给旧版本评价任何优化按钮**（不是置灰提示，是直接没有按钮）；切版本/切章都刷新。
- 验证：tsc 通过；CDP 探针确认徽标、按钮数（恒为 1）、切 v1/v2 后徽标翻转。测完已把第 1 章 active 还原回 v1。

## 九、设定漏写却评不出来 —— 新增确定性核对 services/setting_checker.py
- 用户报：第 2 章正文漏了系统面板的「兴趣爱好」，评价师给 92 分且只字未提（第 3 章却报了）。
- 三个叠加原因：
  1. 评价师只有「整体印象打分」（6 个 rubric 全是 holistic），蓝图 7815 字几十上百条规则，
     LLM 通读只能抽查 → 漏检是常态、抓到是运气（第 3 章两次评价对同一问题一个 medium 一个 low）。
  2. **评价师完全看不到设定库**：上下文只有 蓝图+大纲+故事状态+伏笔账本+关系图谱，
     settings 表一条都没喂（小说家一直看得到 → 单向缺口）。
  3. 原有 blueprint_checker 只核对「导入文档 vs 蓝图」，没有「正文 vs 设定」。
- 方案（用户选：设定库 + 确定性核对 / 命中项作为待确认项强制回应）：
  - 新建 `services/setting_checker.py`：核心是**共现约束**——把「天赋清单+兴趣爱好+适配推荐」
    当一组，组内**至少一个**在正文出现才触发（说明本章写到了这个概念域），**其余没出现的**算漏；
    组内一个都没出现 → 不触发（避免"本章没写系统面板"误报）。
  - 四道降噪：① 只认 `+` `＋` `/` `／`，不认「、」；② **术语边界修正**（中文无词边界，
    靠语料频次把误吞前缀切掉：`容为天赋清单`→`天赋清单`）；③ 组内每术语在语料 ≥2 次；
    ④ **必现锚点**（组前需出现 固定内容/必须/包含/包括/组成/要素/字段/必备），
    否则判定为"备选枚举"（如 良好/优秀/卓越/天才 是等级档位）→ 丢弃。
  - ⑤ 支持蓝图 `content.setting_checks` 显式清单，有则完全免抽取。
  - `agents/critic.py`：补喂设定库（与 novelist 同一份 `filter_settings_for_chapter`，注意
    `get_settings_snapshot` 已过滤软删，表里 27 行实际只有 7 条有效）+ 注入核对清单；
    SYSTEM_PROMPT 增加铁律：核对清单每条必须二选一回应（写入 issues type=setting_check，
    或在 comment 里说明本章不适用），**不允许沉默**。
- 实测：第 1/3 章三项齐全 → 0 命中；第 2 章 → 精确命中「天赋清单+兴趣爱好+适配推荐，缺失：兴趣爱好」。
  dry_run 实跑评价师，新产出 issues[0] 即为该问题（medium）。dry_run 不落库，数据无污染。
- 小坑：锚点窗口写 `blob[start-14 : start]` 会漏判——"面板固定内容"的"容"被算进组内，
  导致 marker 被切两半；改成 `blob[start-14 : start+12]` 才命中。测完已把第 1 章 active 还原回 v1。
